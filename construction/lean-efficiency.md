The advisory estimate remains 220,000 tokens with low confidence and explicit telemetry gaps. No native goal cap.

## Phase 2 acceptance and Phase 3 routing

Phase 2 used one Sol/high implementer, no extra specialists, and Luna/medium
for all five lean proof calls (three validation attempts, builder, reviewer).
The first two validation attempts failed on ambiguous response instructions.
The runtime rejected them; explicit digest and findings semantics fixed the
prompts without weakening evidence checks. All attempts remain in the proof
cost. The three-attempt validation total essentially matched the legacy
baseline, so no material savings claim is justified. The small implementation
used two calls, but has no matched implementation baseline.

Lessons applied: expose one canonical digest to reviewers; distinguish defects
from positive observations explicitly; retain failed usage; test installed
behavior before acceptance; avoid repeated full-suite runs after prompt-only
repairs. Phase 2's broader suite passed 462 tests, followed by six focused tests
for the final prompt/CLI repair and real installed proofs.

Phase 3 uses Sol/high for daily single-owner scheduling, authority and global
metric joins. One Terra/medium UI helper is permitted only with disjoint
ownership and a fixed API contract. The advisory 180,000-token estimate remains
low-confidence; child usage coverage is unavailable. Root's goal-service
aggregate is not a phase-specific invoice or a count to add to provider proof
usage. Root stays accountable until observed GM acceptance, not configuration.

## Phase 3 acceptance rework and construction cost

The first assembled suite passed 474/475 tests; the streamed-observer timeout
exposed an SSE shutdown defect. Installed browser acceptance also caught
GM-disabled metrics disappearing and duplicated expanded Overview loops. These
repairs are required behavior, not extra scope. One failed GM transport attempt
resulted from a missing executable directory in the private proof PATH; its
unavailable usage is retained and the daily identity is not retried in place.
Subsequent non-inference probes corrected that initial diagnosis: the actual
adapter rejection was the proof's zero allowance versus a 20,000-token route
estimate. An early startup validation now prevents that mismatch. The successful
scheduled GM proof consumed 15,906 tokens; duplicate and unchanged requests
consumed no additional inference. See the proof record for both failed fixtures.

The Manager goal service reported 1,995,917 aggregate tokens at 8,201 seconds
during final acceptance. Categories and child inclusion are unavailable, so
this is not a phase allocation or amount to add to specialist/provider totals.
The initial combined phase estimate was 580,000 tokens; the aggregate is well
above it, but the measurement scopes are not comparable enough for a precise
variance. This construction run does not itself demonstrate efficient
orchestration. Subsequent work should use compact fresh task briefs, one
consolidated acceptance pass, and deterministic receipt extraction. Retaining
this long-lived historical Manager context is a material known source of
coordination overhead; no claimed savings should exclude it.

At closeout the goal service reported 2,361,459 aggregate tokens and 10,032
seconds. The same attribution and inclusion limitations apply. This is an
observed construction overrun, not evidence of achieved efficiency savings.
All three phases are accepted; future work should start from a compact brief
rather than carry this historical conversation into another implementation.
