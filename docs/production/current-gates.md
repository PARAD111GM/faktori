# Current production gates

**Status as of October 13, 2026:** FAKTORI is progressing through a private source and installed-package qualification. Source changes and checks remain in progress; no source or package release from this increment has been published. The first incomplete gate is a single linked, installed attended journey from real requirements discovery through an accepted definition and design, generated implementation, independent acceptance, delivery, observed adoption, and the next requested feature cycle.

The production target remains the complete lifecycle for both new products and existing-product changes: discovery, accepted definition, design and architecture, coherent implementation, independent verification, release, observation, and continued development across web, native iOS, and native Android. A qualified coordinator, isolated feature slice, or deployed synthetic app does not establish that lifecycle.

## Evidence that currently qualifies

- **Public attended web exercise:** The synthetic shopping-list application passed its eight-gate browser/API journey, same-image-and-volume restart recovery, and exact-image stopped local backup restore. Schema-2 actual adoption and restore are complete for this exercise. It does not prove generic installed deployment, public browser restore, real-owner discovery, or full FAKTORI readiness. See [attended public qualification](attended-public-qualification.md).
- **Native app exercise:** The shared-backend candidate passed retained iOS Simulator and Android Emulator journeys, including sign-in, shared state, offline queue recovery, and session expiry/recovery. This qualifies simulator/emulator behavior only. Physical devices, production signing, store distribution, and full FAKTORI-generated native delivery remain open.
- **Native supervision source:** The v0.2.14 source implements the bounded app-server supervisor and its fifteen-gate owned fixture journey independently cleared. Streaming executable hashing, supported argv and the protected complete MCP inventory guard passed source and installed checks. Real paused-goal metadata and process exit were observed. Actual activation then started an unsolicited native turn before the explicit request; the supervisor stopped and retained uncertainty. No automatic witness or full-feature acceptance was issued from that failed attempt. Continue through attended bounded execution. See [native supervision](native-supervision.md).

## Open gates, in order

1. **Complete the attended product lifecycle.** Connect actual requirements discovery to a separately accepted product definition and design, generated implementation, independent acceptance, an authorized release, observed adoption, and a subsequent owner-requested feature. Include both greenfield and existing-product paths. The current web receipts are separate synthetic exercises; the linked real-owner journey is not yet proved. Close with one retained evidence chain bound to the same accepted scope and revisions, plus observed delivery and follow-on work.
2. **Finish source and installed qualification.** The streaming-digest, argv and MCP-exclusion repairs passed source typecheck/build, independently reviewed fifteen-gate acceptance and clean-installed-package feature journeys on the frozen v0.2.14 candidate. New implementation changes require their applicable complete-slice checks and installed qualification before release. No source publication is implied by these checks.
3. **Qualify real native supervision or retain attended operation.** Prove the installed native transport's bounded activation, one requested turn, exact terminal observation, paused goal, idle wake, restart, cancellation, disconnect handling, and no duplicate launch against the real supported runtime. Bind an expiring readiness witness to the exact source and independent evidence. Otherwise keep automatic dispatch unavailable and continue through the attended route.
4. **Complete human holdout and evaluator calibration.** The plan requires ten idea briefs including at least three unseen cases, human-authored critical holdouts, 20 human-labeled cases, at least 90% agreement with no critical false acceptance, and calibrated multimodal usability. Generated fixtures and independent source review do not substitute for human labels. Close with retained holdout definitions, labels, results, and calibration evidence.
5. **Qualify supported platforms and release operations.** Prove the claimed installed paths, including real Node and Python work, platform-specific native builds and runtime behavior, supported update/restore, release provenance, and the applicable signing/distribution route. Physical-device and store qualification remain required for claims that include those routes.
6. **Observe sustained accepted outcomes.** The full qualification requires a 14-day cohort and 20 accepted outcomes across Node and Python task classes, with comparable baselines and measured human attention, usage, and outcomes. This is a distinct observation gate; it is not the transport investigation time box.

## Separate decision rules

The plan's **ten engineering-day transport exit rule** applies only to safe transport qualification: if there is no observed safe launch, inspect, goal, and supervision path by then, stop that implementation attempt, document the capability boundary, and proceed with attended product delivery. It is not a 14-day soak, an inference allowance, or a waiver of native delivery gates.

The **14-day / 20-accepted-outcome cohort** measures sustained product performance after usable delivery exists. It does not close human calibration, source/installed checks, real native supervision, or publication authority by itself.

Owner review, source publication, package release, provider activation, deployment, and live-product operation remain distinct authority and evidence gates. Report each only when its own retained evidence exists.
