# Bounded native supervision

This opt-in profile adds one owned Codex app-server connection at a time to the existing coordinator. Bounded `codex exec` remains the default. This release's offline protocol fixture is not native runtime, independent product acceptance or automatic-operation proof.

The installed `0.162.0-alpha.17.2` executable generated the experimental JSON schema without inference. It exposes `thread/start`, `thread/resume`, `thread/read`, `thread/goal/get`, `thread/goal/set`, `turn/start`, `turn/interrupt` and terminal notifications. Schema presence does not prove vendor lifecycle behavior. The older 0.146 goal observation cannot qualify this profile.

The first real metadata qualification rejected the installed 246 MB signed executable before spawn under a 200 MB whole-file cap. The repaired profile streams its pinned digest in 256 KiB chunks with a 512 MiB maximum, retaining canonical-path and file-identity checks. The failed attempt remains evidence; this repair alone does not qualify native runtime behavior.

The next metadata attempt reached the native parser but rejected `--ignore-user-config`, an `exec` flag unsupported by app-server. Its private failure and zero protocol requests remain evidence. The repaired argv uses the pinned app-server's documented stdio, strict-config and feature/config overrides: native ChatGPT login, OpenAI provider, no approvals, disabled apps/plugins/memories/multi-agent/hooks/browser/computer tools, disabled web search and analytics, and disabled skill MCP dependency installation. After initialization, `account/read` with `refreshToken:false` must observe a ChatGPT account before any thread creation; it neither logs in nor exports credentials. Account identifiers and raw protocol bytes remain private. Exact thread responses must still bind the requested model and OpenAI provider with provider fallback disabled.

App-server lacks `exec`'s user-config/rules exclusion flags. Existing user/project configuration, rules, native provider definitions, imported libraries and native credential implementation remain a trusted local boundary. Disabling apps and plugins alone does not establish configured MCP exclusion. The protected per-server guard below binds a complete known inventory; it does not establish wildcard exclusion of future servers or general filesystem/network isolation. This profile cannot be used where exclusion of all ambient native configuration is required. Unsupported configuration, missing ChatGPT mode or provider/thread mismatch fails closed; no API fallback is introduced.

`NativeSupervisionConfiguration` pins a profile/factory, exact executable digest, canonical workspace and private artifacts directory, explicit model/reasoning, native-access approval and separate `boundedTurnApproved`. Limits cap each operation at ten runtime minutes, eight MB captured output and 128 KB context; these are not a token or money cap. An exact allowlisted environment supplies the existing native account. Inference requires `mcpExclusion: {path, sha256}`; its canonical private manifest must remain outside the writable workspace, and both path and exact digest participate in the profile digest. API keys, ambient Node hooks, provider fallback and separate billing are excluded. The executable digest does not seal its interpreter, libraries, vendor credential implementation or OS; native sandbox requests are not a claim of filesystem isolation.

The retained actual baseline and `mcp_servers={}` experiments each returned the same 14 configured servers and 40 tools. Empty TOML tables merge into ambient configuration rather than remove its entries. A separate native metadata experiment applied documented per-server `enabled=false` overrides and disabled `skill_mcp_dependency_install`; its complete owned-thread inventory contained all 14 entries as disabled with zero tools or resources. No active goal or turn was requested. This establishes the tested per-server mechanism, not portable wildcard removal, general network exclusion or automatic qualification.

The strict `faktori.native-mcp-exclusion/v1` manifest contains `protocolVersion` and unique `serverNames` (at most 400, at most 100 characters each). Safe raw names may use letters, numbers, underscore, hyphen, `@` and `/`; dots, quotes, equals and control characters are excluded. Every `mcp_servers.<name>.enabled=false` override is one shell-free argv token. Native dotted-path parsing does not require literal TOML quotes around names. The transport rereads the manifest's bounded exact bytes and verifies canonical file identity, private ownership and digest before spawn; it exposes the exact applied binding for the supervisor to compare. Startup passes the same binding to configuration and transport.

Fresh guarded preparation retains a complete scoped inventory. Every fresh or resumed execution rechecks the protected manifest and the already-owned loaded thread's complete `mcpServerStatus/list` inventory before goal activation and before the explicit turn. The complete inventory must cover every manifest name exactly once, every runtime status must be disabled, and tools, resources and templates must be empty. Pagination is bounded to four pages of 100 with no remaining cursor or repeated names. Unknown names, enabled tools, missing status, incomplete inventory, changed bytes or a transport/profile mismatch fail closed. Native MCP startup notifications under a guarded profile invalidate execution; private guard snapshots bind the observed inventory to the same thread and manifest. An interrupted attempt cannot retry these effects or restore authority through inspection. Metadata-only profiles without inference permission may omit the manifest and retain the explicitly trusted native MCP boundary.

`TaskSupervisor.prepare(intent, context)` requires an admitted exact RunIntent and approved context payload. It records preparation intent before creating a persistent owned thread, records the returned identity before setting a **paused** goal, and retains private prompt/protocol provenance. Interrupted creation is not retried or inferred from the most recent thread. Preparation never sends a turn or an active goal.

`CodexAppServerAdapter.start` prepares after the existing delivery admission, then executes only when bounded-turn permission is explicit. It resumes the exact owned thread, verifies idle state and the paused objective, revalidates authority/context, activates and observes the exact goal, and requests one explicit bounded turn. Unsolicited activation/turns before that request or a second turn after terminal evidence leave the attempt uncertain. Routine status uses protocol notifications and deterministic observation, without an LLM heartbeat. The goal is paused after the exact terminal turn and the owned process group must exit before completion is retained.

Private artifacts retain protocol captures. The coordinator keeps content bindings and safe outcome summaries. Duplicate identical terminal notifications are harmless; conflicting IDs/results, disconnect, output overflow, timeout, failed bookkeeping or uncertain process exit preserve capacity and prohibit another launch. `inspect` reads only the recorded thread; it does not turn missing terminal evidence into permission to retry. Explicit same-scope resumes require a completed durable source, exact current context and unchanged factory/product/repository/workspace/role. They do not reuse a builder conversation for independent review.

Control storage must be outside and disjoint from the model's writable workspace: artifacts, executable, coordinator journal/lock/projection, witness, MCP exclusion manifest and independent evidence. Canonical path checks apply in the module before native effects and readiness observations; private permissions alone do not protect same-UID records from model tools. Read-only inspection may observe revoked owned runs without restoring execution authority. Early handshake notifications are retained and checked in preparation, execution and inspection. Concurrent identical cancellation requests share one native interrupt and completion.

File-based Console startup also resolves the owner configuration to its canonical path and excludes it from the native writable workspace before startup effects. Settings changes retain that canonical control file and must preserve the boundary; a restart rechecks the actual workspace path.

`TaskSupervisor` implements `WorkflowTrustedReadinessPort`; Console startup must inject this trusted instance through `ConsoleQueueBridge`. An owner configuration boolean or fixture cannot enable automatic operation. Native-goal readiness also requires inference authority and an unchanged protected MCP exclusion binding; absent or changed bindings remain unready even with a witness. An exact private `faktori.native-supervision-witness/v1` operator attestation must bind the current profile/source, a retained completed qualification run and seven independently retained passing evidence files: transport, native goal, idle wake, restart, cancellation, candidate verification and runtime verification. The observation and attestation expire within two minutes. Every handoff rereads source/evidence and native state. `nativeGoal.ready` means the **qualified guarded capability** is available; it does not claim paused goals are active. Actual activation is verified at the authorized execution handoff.

Before accepting a real witness, qualify exact 0.162 activation → one requested bounded turn → exact terminal → paused goal → no extra native start. Observe restart/disconnect/cancellation and an independently accepted full product feature on a private approved workspace. If goal activation itself starts inference or vendor continuation escapes the bound, retain the blocker and use attended `exec`; do not imitate an unsupported desktop scheduler. No third-party chats, tickets, notifications, hosting or release authority are introduced.

The single `scripts/accept-native-supervision.mjs` journey supports `FAKTORI_ACCEPT_CLI` for source/installed modules. Its owned local JSON-RPC executable is explicitly a fixture. Real native account/runtime and automatic qualification remain separate evidence gates.

## Observed native execution boundary

On October 13, the frozen v0.2.14 source, typecheck/build, independently reviewed
fifteen-gate journey and clean installed-package checks passed. The real bounded
qualification then observed the supported native runtime start a turn when
`thread/goal/set` activated the goal, before any explicit `turn/start` request.
The supervisor rejected this unsolicited turn and retained an uncertain result;
the synthetic backend evaluator did not run and no passing witness was issued.
The original failed attempt and exact-owned containment observations are retained
privately. Native-goal automation remains unqualified for this runtime. Continue
product delivery through the attended bounded `exec` route; its evidence is
separate from native-goal supervision.
