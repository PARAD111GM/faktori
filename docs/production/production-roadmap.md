# Production application factory roadmap

The accepted production mandate extends the original V1 construction plan:
raw idea → requirements discovery → sourced product definition → design and
architecture → full feature implementation → independent acceptance → production
delivery → observation and ongoing feature development. Produced applications
include web and native iOS/Android. Existing products enter through proportional
discovery of the requested change and the live compatibility baseline.

This roadmap tracks the accepted October 12 production plan and adversarial-review
sequencing. The original V1 implementation plan remains historical architecture
and construction context. [Execution status](execution-status.md) records what
has actually been observed; source implementation never closes delivery gates.

## Release sequence

| Outcome | Implementation and acceptance | Recovery and release gate |
| --- | --- | --- |
| Inventory and attended spike | Exercise existing lifecycle skills; record actual provider execution, independent controller acceptance, full artifacts and every manual bridge | Retain failed candidates, exact evaluator/candidate identities and resume without duplicate execution |
| v0.3 attended production web | Integrate discovery/definition, design/context and delivery; qualify one complete authenticated persistent web product on approved public infrastructure | Verify exact deployed artifact, HTTPS, isolation, failure/retry, restart, logs and independent backup/restore before admission |
| v0.4 ongoing live web development | Adopt the deployed baseline; discover and implement a real feature while preserving clients, contracts, data and concurrent work | Rehearse migration and rollback/forward recovery; independently prove signed-in behavior and the intended outcome after release |
| Native feasibility alongside web | Build and run one shared native codebase on iOS and Android; exercise required native behavior | Retain real build/runtime receipts; local simulator evidence does not establish device/signing/distribution |
| Qualified automatic profile | Admit a narrowly defined profile using observed transport, worker supervision, independent acceptance, bounded repairs and durable restart reconciliation | Require measured cost/attention and the accepted ten-day observation exit rule; pause on lost authority or uncertain execution |
| v0.6 complete native delivery | Qualify shared backend/client contracts, lifecycle, offline/reconnect and required device permissions/capabilities; produce signed iOS/Android artifacts | Physical-device and distribution receipts, client/version compatibility, store authority and recovery remain separate gates |
| Full production qualification | Prove the installed owner journey across new web/native products and ongoing live feature releases | Human-authored critical holdouts/seeded defects, calibrated evaluation, security/data/incident ownership, restore evidence and release/update observation |

## Implementation workstreams

- APP-01 owns adaptive discovery, immutable product knowledge, complete sourced
  definitions, uncertainties and requirement amendments. Model interpretations
  remain proposed; owner declarations are distinct from observed evidence.
- APP-02 owns product experience, interaction/error states, accessibility,
  architecture and coherent executable slices. Accepted requirements and design
  feed scoped context and dependency-aware delivery.
- APP-03 owns web build/runtime/release adapters and observed public operation.
  A generated screen or local container is insufficient for production delivery.
- APP-04 owns one shared native codebase by default, target build/device/release
  adapters and shared backend compatibility. A WebView wrapper is insufficient.
- APP-05 owns live baseline registration, feature impact, migration/client
  compatibility, staged release and observed outcomes feeding the next cycle.
- PRD runtime work owns native transport qualification, durable worker identity,
  authority, evaluator integrity, budgets/attention, evidence, recovery and
  packaging. Expand automatic admission only after the attended path supplies
  the evidence applicable to that profile.

Implement complete feature slices and run minimal acceptance across their full
positive, failure and recovery journeys. Existing historical unit tests are
retained; no micro-unit testing loops are used. GPT-6-Luna handles straightforward
bounded work and GPT-6.1-Sol handles complex integration and independent review.
Provider credentials remain in the unchanged vendor CLI. Account, spending,
signing, publication and release effects require their actual owner authority.

Prioritize the next gap using observed acceptance failures, repeated manual
bridges and total human effort. Time estimates, code volume, model activity and
green package checks do not establish completion. Requirements discovery,
web/native production delivery and ongoing live development remain central
through every release tier.
