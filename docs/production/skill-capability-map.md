# Shipped skill capability map

**Evidence basis:** repository revision `3c9de5ed520d74ef0a92b574265e576db96c7928` (the requirements-discovery spike base). This inventory is a source review, not an agent-behavior evaluation or production journey. “Guidance” means a skill tells an agent what to do. “Executable seam” means repository code implements a bounded portion of that behavior. Neither implies a complete installed journey.

## Implementation after the inventory

The inventory below retains its original base evidence. Subsequent executable
work adds immutable raw-idea interviews, exact native model proposal capture,
definition/requirement/scenario validators, scoped delivery compilation,
web/iOS/Android release contracts, live-baseline constraints and durable
intervention records. The v0.2.9 draft bridge carries the full interview into a
sourced proposal-only product definition. It rejects changed owner intent,
platforms, live baseline, stale snapshots and model-supplied approval.

Subsequent observed qualification includes the approved synthetic public web
exercise and schema-2 baseline adoption/restore, shared-backend iOS Simulator and
Android Emulator journeys, and actual bounded Node/Python generated-feature
acceptance. The installed native-local artifact/adoption seam also passed.
The production signing/distribution adapter passed separate synthetic source
and installed qualification; the deploy skill identifies its distinct build
and artifact-bound upload approvals. Actual signing/store distribution remain
unqualified.
The linked real-owner lifecycle, human evaluator calibration, sustained outcomes
and qualified automatic operation remain open. See [execution status](execution-status.md) for the
current gates and [definition draft](definition-draft.md) for the new handoff.

## Accepted goal and evidence standard

The accepted owner mandate and preparation criteria are retained in [the implementation brief](implementation-brief.md) and [attended spike runbook](attended-web-spike.md). New-product and existing-product entry paths are both required; requirements discovery must precede technical solution selection, preserve sourced facts/requirements/assumptions/unknowns, and produce sufficient inputs for the next bounded decision. The complete product target includes web, shared-codebase native iOS/Android, and continuing work on live products. This source map precedes application implementation scope; skill guidance is not automated-journey proof.

The existing public lifecycle contract has six outcomes—Plan, Design, Build, Test, Deploy, Maintain—and requires revision-bound evidence and reasons for inapplicable stages ([contract](../lifecycle/contract.md), [implementation plan](../implementation-plan.md#work-hierarchy-context-and-lifecycle-skills)). The context implementation validates hierarchy and assembles scoped packets with lineage and dependency contracts ([context README](../context/README.md), [small-bug example](../../examples/context/small-bug.json)). These contracts are useful downstream foundations; they do not themselves discover product requirements.

## Shared executable evidence and boundary

- **Catalog and portability:** `provider-entrymaps/source.json` declares all 16 skills, triggers, and Codex/Claude/Cursor maps. `scripts/verify-skill-kit.mjs` validates catalog agreement, frontmatter, local skill links/resource boundaries and all provider maps; `tests/skills/shipped-kit.test.mjs` tests this. The check proves package/link structure, not that a model follows a skill. Observed during this inventory: `node scripts/verify-skill-kit.mjs` passed with 16 skills and three entry maps.
- **Lifecycle coverage:** `docs/lifecycle/contract.md` defines six generic outcomes; `tests/skills/lifecycle-artifacts.test.mjs` checks the 16-name catalog and matching Node/Python lifecycle fixture shape. There is no native-app fixture in this evidence set.
- **Discovery/provisioning:** CLI and `src/provisioning/index.ts` deterministically represent inventory, owner answers, unknowns, proposal effects, explicit approval, local file provisioning and recovery. This is not an adaptive question-asking or app-specification engine. The supplied interview fixture is a factory-configuration example, not a generated production product definition.
- **Behavioral evaluation:** `docs/skills-evaluation.md` specifies dry-run scenarios A–G plus update. `docs/build/sdlc-skills-report.md` says probes A, C, D, E and F were instruction-level dry runs; B, G and update are not claimed as completed probes there. It explicitly says native auto-discovery and live execution of the scenario set were not demonstrated. No row in this map upgrades those dry runs to installed or production evidence.

## Gaps to close before committing application implementation scope

1. **Discovery contract:** Add a product-definition artifact and source/decision/assumption/unknown traceability covering every section-0 required output, with adaptive scale: raw idea and existing-product paths; users, outcomes, journeys, functional/domain/error/permission behavior, NFR, data/roles/integrations, reusable resources, live baseline and compatibility, prioritized scope/exclusions, and testable acceptance scenarios.
2. **Platform and product type:** Add an explicit web/iOS/Android target contract, device/OS envelope, native capability and distribution/signing ownership. Default mobile to one cross-platform native UI codebase; require a recorded product-specific exception for separate native codebases and reject WebView wrappers as satisfying native acceptance. Discover live web/native compatibility and client constraints for existing products.
3. **Lifecycle traceability:** Link discovery requirements to accepted definition, design decisions, work nodes/context, implementation, independent acceptance cases, deployment artifact, post-deploy observations and amendments. Define which revision changes invalidate downstream evidence and how prototype/implementation discoveries reopen intent without silently rewriting it.
4. **Executable/evaluator boundary:** Identify deterministic schemas/validators and installed commands for durable product-definition creation, requirement-to-scenario coverage, context assembly, platform build/test, staged delivery and observed outcome. Keep model judgment for product understanding and multimodal review, while owner-controlled/evaluator-owned evidence establishes criteria and integrity. Do not describe skill text, generated sample output, a command exit, or a dry run as an automated journey.
5. **Qualification scenarios:** Extend the behavior set from the existing generic A–G probes to human-authored greenfield and brownfield idea briefs with held-out cases and seeded critical defects. Score requirement coverage, unsupported assumptions, missed material questions, traceability and acceptance quality; separately demonstrate web, native iOS, native Android, existing live web and existing live native end-to-end journeys. Preserve explicit owner/resource/provider gates and evidence provenance.
6. **Inventory/report freshness:** The older [skill-kit report](../build/sdlc-skills-report.md) now distinguishes its historical fifteen-skill scope from today's sixteen-skill catalog. Historical archive/probe verification and explicit limits remain intact; no later app journey is inferred.

**Current disposition:** the shipped kit provides broad, carefully bounded lifecycle instructions and real provisioning, context, test, delivery, maintenance and runtime seams. Its strongest current discovery support concerns configuring a factory and registering products. Requirements discovery for a production application, native mobile production, independent product evaluator integrity, and the complete installed discovery-to-observed-production chain remain **guidance-only, partial, or unverified** as stated above. PRD-01 mapping is complete at source-review level; PRD-01 behavioral and end-to-end acceptance is not established by this document.
