# Faktori v0.2.0 release notes

Released as an experimental local development-kit release. Faktori v0.2.0
strengthens the path from an installed kit to an honestly described factory; it
does not claim a hosted service, a universal one-command erection, or a
whole-system E2E acceptance.

## What is included

- Projects organized into plans, phases, and tickets, with list-to-detail navigation.
- One ticket-backed Work Kanban for local and Jira work, project/search filters,
  linked executions, bounded column heights, and inset scrolling.
- Durable Decision Inbox, recorded session assignments, qualified progress,
  and separate factory-health versus delivery-blocker views.
- Settings editing with actionable missing-configuration guidance; single dark
  page headers, consistent controls, and nested section cards.
- GitHub verification workflow running deterministic checks without paid inference.

- The local TypeScript runtime, packed CLI, Console, recoverable records, and
  maintenance/update path already documented by this repository.
- The 16-skill SDLC kit and provider entry maps for Codex, Claude Code, and
  Cursor.
- Local work management, optional read-only Jira observation, and opt-in
  Factory GM/scheduler configuration.
- A deterministic setup-readiness report and agent guidance that surface missing
  provider routes, Jira authorization, and GM scheduling as explicit states.

## Integration truthfulness

Every v0.2 handoff must inventory selected provider routes, Jira mappings, and
GM scheduling as enabled-and-verified, pending auth/observation, or deliberately
owner-deferred. The inventory report is offline and redacted; it cannot prove
Jira access, Claude authentication/execution, GM scheduler health, provider
spending, or product delivery.

A provider appearing in the catalog is not a configured/authenticated route.
A configured GM is not an observed scheduler. Jira uses a single server-side
authorization reference per Jira site, reusable for the owner's mapped projects;
unmapped Faktori products use local tickets.

## Upgrade boundary

For an existing factory, create/review a backup and the exact update preview
before applying a release. Preserve records, owner material, credentials, and a
recoverable prior runtime. Do not restart workers, copy credentials, or change
authentication, spending, billing, or provider permissions as part of an update.
Use [the agent update guide](../agent-update-guide.md) and
[maintenance documentation](../maintenance/README.md) for the operational path.

## Evidence boundary

The release's local build/package checks and deterministic fixtures are not live
provider, Jira, scheduler, host-wide, or product-journey proof. Phase 7's Twinzy
proof and final release acceptance remain owner-deferred/blocked as documented
in [Phase 7 evidence](../build/phase-7-report.md). Treat new live integrations
as separate approved, bounded exercises with their own observed evidence.
