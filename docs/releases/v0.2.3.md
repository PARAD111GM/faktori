# v0.2.3 — Delivery recovery foundations

## Source changes

- Graph-backed `delivery plan` reuses the validated hierarchy and context
  assembler: eligibility precedes rank/capacity, affected upstream changes
  invalidate dependency evidence, and newer tracker blockers cannot disappear
  from a stale graph projection. Planning nodes cannot be dispatched.
- Optional owner-triggered graph enqueue connects that planner to the existing
  Console relay, requiring current catalog scope and a readiness-bound private
  packet. It queues work only; automatic scheduling and native task execution
  remain separate verification gates.
- Explicit `automaticGraphDispatch` enables bounded, single-owner relay queue
  replenishment from approved graph packets and observed relay state. Unchanged
  inputs skip evaluation; busy/uncertain assignments reserve capacity and terminal
  assignments are not replayed. This does not yet automate the complete delivery
  chain or establish idle-Foreman wake-up.

- Read-only `delivery inspect` joins a configured Jira sprint and registered
  GitHub PR observations without guessing review or deployment acceptance.
- Delivery synchronization helpers discover transitions per issue, check
  eligibility before capacity, preserve human-owned statuses and require
  separate staging acceptance before an accepted-status transition.
- Delivery observation reconciliation refreshes tracker/PR/check facts while
  preserving only exact-revision independent evidence. Signed-action composition
  and a final Jira evidence hook connect planning to guarded mutations; installed
  Console wiring remains a separate gate.
- Slack outbox and signed-action adapter retain durable intent, serialize
  subjects, distinguish delivery from acknowledgment and reconcile ambiguous
  delivery before retry. Private credentials remain outside records.
- Slack ticket correlation accepts bounded project ticket keys instead of a
  hardcoded Twinzy prefix; signed notification and destination controls remain
  required.
- Opt-in Manager-connected sprint admission rechecks current goal/context
  observations and artifact hashes at enqueue and claim, refuses duplicate
  assignments, and caps builder/implementer claims at three. Legacy relays remain
  unchanged and visibly unconfigured for sprint readiness.
- Artifacts navigation reuses safe project content, exposes missing/unavailable
  intent and preserves the distinction between snapshots and file observations.
- Work shows a read-only, fail-closed Sprint readiness panel.
- Recovery readiness requires explicit dispatch-ownership evidence so that an
  existing Triforge scheduler or surviving worker cannot be ignored at cutover.
- `sprint goal <codex-task-id>` observes a native goal through the vendor
  app-server without starting inference or changing the task. Missing, inactive
  and unavailable states fail closed; it does not grant sprint admission.
- Recovery-mode relay claims require fresh active Foreman and builder goals,
  then recheck the approved readiness binding before handing off work. A stale
  passing document cannot substitute for a goal that has ended. Dashboard
  polling and legacy relays do not launch these diagnostic processes.

## Installation and acceptance

- Added an opt-in Console-hosted delivery synchronization controller using
  existing signed grants, live Jira/GitHub observations, and the action journal.
  Existing installations remain disabled unless explicitly configured.
- Factory now distinguishes synchronization that is not configured, blocked,
  or monitoring. This status never substitutes for staging acceptance.
- Missing or unsafe private packets fail closed without stopping the Console.
  The setup guide documents the controller contract and remaining setup limits.

This is not a claim that the failed installed factory has been restored.
Source adapter tests do not prove deployed n8n routing, goal evidence collection,
Foreman wake-up, automatic signed-action wiring or the connected staging journey.
Those remain release-acceptance gates. No live Jira mutation, notification,
merge, product deployment or active-worker restart is included.

Read [Recovery setup](../recovery-setup.md) and the
[integration inventory](../recovery-inventory.md) before enabling admission.
Keep canonical artifacts in the project, not in an installation update folder.
Reuse existing approved authentication and configured channels. A missing
connector or an HTTP success is not a passed capability check.

Rollout is opt-in after inspection and worker reconciliation. Preserve journals,
existing candidates and uncertain operations. Disable new admission on failure;
do not delete locks or records to force retries. Asad's merge authority is
unchanged. No outcome-efficiency savings are claimed without measured delivery.
